# Store Footfall & Sales Conversion Analytics

An end-to-end retail analytics platform built with **Databricks, Snowflake, FastAPI, React, and Netlify**.

The system takes store, footfall, and billing data through a reproducible data-engineering pipeline, applies documented data-quality rules, produces a business-ready Gold dataset, loads analytical data into Snowflake, and exposes the results through a web application.

The application supports both a **Demo Mode** using the official reproducible project dataset and an **Upload Your Data** workflow for processing new datasets that follow the supported schema.

---

## 1. Project Overview

Retail stores often have two separate operational signals:

- how many people visit the store
- how many bills are generated

Looking at either signal independently does not answer the business question of whether increased traffic actually converts into sales.

This project brings both signals to the same **store + date + hour** grain and produces analytical insights around:

1. Conversion rate per store per hour
2. The three lowest-conversion hours across the chain
3. The relationship between footfall intensity and conversion

The project demonstrates a complete modern data-engineering workflow:

# 6. Medallion Architecture

## Bronze

The Bronze layer lands the raw data without cleaning it.

All source columns are preserved as strings and three provenance columns are added:

```text
_source_file
_ingested_at
_row_hash
```

Bronze preserves raw values such as:

```text
ERR
OFFLINE
0
```

and intentionally retains duplicate records.

Bronze tables:

```text
workspace.capstone_peeyoush.bronze_stores
workspace.capstone_peeyoush.bronze_footfall
workspace.capstone_peeyoush.bronze_bills
```

---

## Silver

Silver applies the documented data-quality decisions.

### Type conversion

`try_cast` is used instead of `cast`.

This allows invalid values to become `NULL` so they can be counted and reported rather than causing the pipeline to fail.

### Footfall cleaning

```text
300 ERR values -> NULL
240 OFFLINE values -> NULL
```

The `sensor_ok` flag identifies usable sensor-hours.

### Bill cleaning

```text
86,859 raw bills
-   130 duplicates
-    75 unknown-store bills
-    60 out-of-hours bills
= 86,594 valid Silver bills
```

Rejected records are stored with explicit rejection reasons instead of being silently discarded.

Silver tables:

```text
workspace.capstone_peeyoush.silver_stores
workspace.capstone_peeyoush.silver_footfall
workspace.capstone_peeyoush.silver_bills
workspace.capstone_peeyoush.silver_rejects
workspace.capstone_peeyoush.silver_store_hour
workspace.capstone_peeyoush.silver_quality
```

# 9. Snowflake Architecture

Snowflake is used as the analytical warehouse.

Objects:

```text
CAPSTONE_WH

CAPSTONE_DB
└── ANALYTICS
    ├── CAPSTONE_CSV_FORMAT
    ├── GOLD_STAGE
    └── GOLD_STORE_HOUR
```

The Gold CSV is uploaded to the internal Snowflake stage and loaded with:

```sql
COPY INTO CAPSTONE_DB.ANALYTICS.GOLD_STORE_HOUR
```

The load process is validated by running `COPY INTO` twice and confirming that the already-loaded file is not duplicated.

# 11. Business Questions and Results

## Q1. Conversion Rate per Store per Hour

Conversion is defined as:

```text
conversion_rate = bills / footfall
```

only when the sensor reading is valid and the footfall value is positive.

The dashboard exposes this metric at both hourly and store levels.

---

## Q2. Three Worst Hours

The chain-wide lowest-conversion hours are:

```text
14:00
15:00
16:00
```

The exact ordering is based on the measured conversion values.

These hours are intentionally lower because the generated dataset applies an afternoon conversion penalty while traffic remains measurable.

---

## Q3. Does Conversion Drop on High-Footfall Days?

Store-days are bucketed into ten footfall deciles independently for each store.

The resulting analysis shows that the highest-footfall decile converts at a lower rate than the lowest-footfall decile.

This provides the project's answer to the business question about high-traffic days.

# 19. Data Quality Guarantees

The pipeline intentionally demonstrates real data-engineering problems instead of only processing perfect data.

The implementation handles:

- malformed numeric values
- invalid timestamps
- dead sensors
- duplicate records
- unknown dimension keys
- out-of-hours records
- missing measurements
- reproducible generated data
- provenance tracking
- row-level hashing
- explicit rejection reasons

The goal is not merely to obtain an answer, but to preserve enough evidence to explain how the answer was produced.
